# CTP 开发、测试与生产知识库

> 整理日期：2026-11-24  
> 适用对象：CTP API 封装、交易网关、策略接入、测试与生产运维人员。  
> 文档定位：记录协议事实、环境差异、真实陷阱、工程防线和故障处置，不把某次 SimNow 实测推广为柜台承诺。

## 0. 使用规则与证据边界

### 0.1 三条最高优先级原则

1. **请求发出不等于柜台受理，柜台受理不等于交易所接受，交易所接受不等于成交。**
   `Req*` 返回 0 只说明本地 API 成功发出报文；文档甚至明确不保证随后一定有 `OnRsp` 或 `OnErrRtn`。断线或超时的报单必须进入“结果不确定”，不能直接记为失败并重发。[O6]
2. **柜台状态是交易事实来源，本地状态必须有持久化、去重和对账。**
   回报可能重放、重复、迟到或丢失；报单和成交不是同一种事实，成交记账以 `OnRtnTrade` 为准。
3. **SimNow 连通和下单成功，只证明该环境下的一条路径可走。**
   它不能证明期货公司的认证、权限、流控、合约参数、交易所规则、清算流程和生产网络均已通过。

### 0.2 证据等级

| 等级 | 证据 | 使用方式 |
|---|---|---|
| A | 当前项目随包 SDK 头文件、`error.xml`、目标柜台当前版本文档 | 字段、枚举和当前错误的优先依据 |
| B | CTP 官方 API 文档、官方开发指南 | 协议和通用行为依据；旧指南必须带版本边界 |
| C | 成熟开源网关实现、官方论坛经验、可复现案例 | 用于设计防御和测试场景，不当作所有柜台的承诺 |
| D | SimNow、OpenCTP、单个期货公司或单次实盘观察 | 只代表对应环境与日期，必须记录版本、柜台和前置 |

本项目当前携带的 SDK 版本以 `README.md` 和 `sdk/include/` 为准。本文引用的 6.7.11 在线文档用于解释通用语义；若与当前随包头文件或期货公司提供的版本说明冲突，以目标环境的当前材料为准。[L1]

### 0.3 环境能力矩阵

| 环境 | 适合验证 | 不能据此证明 |
|---|---|---|
| 本地 mock / 回放 | 状态机、乱序、重复、断线、超时、聚合、持久化 | 真实网络、认证、柜台和交易所行为 |
| SimNow 仿真 / 7×24 测试 | 基础调用链、字段转换、订阅、查询、普通报撤单冒烟 | 生产权限、真实费率、全部交易所差异、故障恢复完整性 |
| OpenCTP / TTS 等兼容环境 | 额外功能测试、长时间连通性、兼容性对照 | 官方 CTP 柜台行为；它是兼容实现，不是生产柜台副本 |
| 期货公司仿真 / 穿透式评测 | 目标公司的 SDK 组合、AppID/AuthCode、终端采集、账户权限和接入流程 | 生产网络、真实资金风险、全部生产流控与动态参数 |
| 生产 | 最终端到端行为 | 也不应被当作可随意做破坏性故障试验的环境 |

SimNow 本身有适用时段不同的多套环境；期货公司仿真账号和穿透式测试账号通常需要单独申请。[P6]

### 0.4 接口开发门禁与审核等级

所有新接口在开发前必须检索本知识库、`FAQ.md` 和网络资料，并先沉淀新发现的陷阱与解决办法。原始绑定、Session 已开发和环境审核是不同状态；Session 的开发审核、测试审核、生产审核分别以实际成功证据从“待进行”更新为“已通过”。

具体开发流程见根目录 `AGENTS.md`，Session 接口的开发、测试与生产审核证据见 [Session层接口.md](Session层接口.md)。历史代码和历史 SimNow 记录不自动获得“已通过”状态。

## 1. 快速症状索引

| 症状 | 优先怀疑 | 首要动作 |
|---|---|---|
| `Init` 后一直无 `OnFrontConnected` | 地址/端口、协议前缀、防火墙、SDK 与前置不匹配、生产/评测模式错误 | 记录 API 版本、完整前置类型和加载库路径；用目标公司提供的链路和客户端对照 |
| 反复 `4097` / `8193` | 网络读写/心跳、版本不匹配、前置连接频率限制、服务端主动断开 | 把 reason 当现象而非根因；检查是否陷入自建重连风暴 |
| 认证失败 | AppID、AuthCode、BrokerID、UserID、环境、账户授权、生产/评测库组合 | 停止无退避重试，与期货公司核对授权绑定 |
| 登录成功但报“结算结果未确认” | 当前交易日尚未确认结算单 | 查询确认状态，未确认时执行确认；不要只按进程启动次数判断 |
| 报“用户在线会话超出上限” | 其他终端、残留会话、测试和生产并发、重复网关实例 | 清点同一 UserID 的全部客户端；不要靠不断重登挤掉别人 |
| `Req*` 返回 -1/-2/-3 | 网络、在途请求、本地/前置流控 | 保存返回值；查询可安全排队重试，报单不得盲目重发 |
| `ReqOrderInsert` 返回 0 后无任何回调 | 请求仍在途、断线、对话流丢失、前置缓存或异常 | 标记“结果不确定”，查询报单和成交，禁止直接重下 |
| 等不到 `bIsLast` | `OnRspError`、断线、空载荷被跳过、请求 ID 串批、超时处理缺失 | 结束在途批次并保留诊断；恢复后重新查询 |
| 重启后成交重复 | RESTART/RESUME 重放、QUICK 与查询快照重叠、应用未幂等 | 按成交唯一键去重，数据库唯一约束兜底 |
| 重启后“漏成交” | QUICK 未补查、RESUME 流文件失效、清流、流文件混用、处理时崩溃 | 以柜台当日成交查询对账；检查流文件和恢复窗口 |
| 委托状态看似倒退或重复 | 多次合法状态通知、CTP 与交易所分段回报、不同事件交叉 | 不假设状态通知只出现一次；累计成交量以成交事实校正 |
| 成交后马上平仓报可平不足 | 只依据报单状态、持仓冻结、在途平仓单、今昨仓错误 | 等成交事实并重新计算可平；检查已有平仓委托 |
| 持仓翻倍或今昨仓错误 | 多行覆盖/重复累加、未按合约+方向+开仓日期聚合、直接使用 `YdPosition` | 每批从原始行重建快照，再发布完整结果 |
| 行情价出现 `1.7976931348623157e308` | CTP 用 double 极大值表示无值 | 转空值，不得进入计算、存储为真实价格或参与下单 |
| 夜盘时间突然多/少一天 | 交易日、自然日、ActionDay 和交易所差异 | 保存原字段；按交易所规则构造时间，同时记录接收时间 |
| 重连后无行情 | 未重新登录、未重订阅、订阅失败未处理、合约已失效 | 重放订阅集合并核对每个订阅应答 |
| 中文错误乱码 | GBK/系统编码转换、定长字符数组未按长度处理 | 在 FFI 边界统一解码；保留 ErrorID 作为稳定检索键 |
| 多账户/多实例偶发丢回报 | 共用 flow 目录、回调对象生命周期、会话标识混用 | 每个 API 实例独立目录、独立状态和独立持久化命名空间 |
| 转账“成功”但未到账，或重复转账 | 把受理当结果、断线后重发、未查流水、冲正 | 查转账流水与资金；结果不明时禁止再次发起 |

## 2. 通讯模型：先分清三种模式与四种流

### 2.1 对话流、查询流、私有流、公共流

- **对话流**：登录、报单、撤单等请求及直接应答。柜台不维护其故障恢复状态，通讯途中数据可能丢失。
- **查询流**：多行查询响应。柜台同样不维护故障恢复状态，断线时在途批次不能指望继续完成。
- **私有流**：报单、成交、错误回报等。一个交易日内支持按序号恢复，但恢复效果受订阅模式、流文件、清流和客户端持久化影响。
- **公共流**：合约状态、公告等公共通知，也是可靠流的一种，但不等于客户端业务状态已经恢复。[O2][G2]

**工程结论：**“TCP 已连接”“已登录”“私有流已恢复”“初始对账完成”是四个不同状态。策略可交易状态必须在最后一项之后才能打开。

### 2.2 私有流订阅模式

| 模式 | 语义 | 主要风险 | 必须配套 |
|---|---|---|---|
| `THOST_TERT_RESTART` | 从本交易日起点重传 | 重启后大量历史回报重放；不能把它当新成交 | 持久化去重、幂等状态归并、启动性能预算 |
| `THOST_TERT_RESUME` | 从本地记录的位置续传 | 流文件丢失/混用、柜台清流后可能收不到 | 独立持久目录、文件监控、清流预案、查询兜底 |
| `THOST_TERT_QUICK` | 只传登录后的内容 | 进程停机或首次登录前的数据不会凭空回来 | 启动/恢复全量查询、快照与增量竞态处理 |

当前 API 文档推荐 RESTART，并明确提示：柜台清流重启后，不删除旧流水文件而继续使用 RESUME，可能收不到私有流回报。这里的“删除”是故障处置线索，**不是常规清理动作**；生产上应先与期货公司确认，并用查询对账，不能在盘中擅自删状态文件。[O4]

OpenCTP 的经验指出，自动重连后的续传行为与进程首次启动并不完全相同。因此不能用“模式是 QUICK，所以任何断线都一定不补”或“RESTART 绝不会重复”替代应用层去重和对账。[P4]

### 2.3 flow 文件不是临时垃圾

- 每个 Trader API 实例必须使用独立 flow 目录；多实例共用可能导致报单回报丢失。行情与交易实例也应分开。[O5][G2]
- 目录要按**环境、账户、实例身份**隔离；是否再按交易日拆分取决于订阅模式和恢复设计，不能一边依赖 RESUME 一边随意换目录。
- 不要把目录放在多个进程同时写的共享位置，不要让测试、生产和回滚实例共用。
- 启动时检查目录存在、可写、磁盘余量、文件句柄和异常退出后的权限变化。
- 备份、清理、迁移和回滚都必须把 flow 文件与业务数据库一起考虑。只恢复其中一个，序号与业务状态可能不配套。

## 3. 认证、登录、结算与会话

### 3.1 推荐连接状态机

```text
Disconnected
  -> Connected
  -> Authenticating（目标柜台需要时）
  -> LoggingIn
  -> LoggedIn
  -> SettlementChecking / Confirming
  -> InitialSyncing（合约、报单、成交、持仓、资金）
  -> Ready
```

任何 `OnFrontDisconnected` 都应立即撤销 `Ready`，停止新交易指令，并将在途查询结束为“连接中断”。重连后重新执行目标环境要求的认证、信息上报和登录，不能只等 API 自动连接。[O3][F2]

### 3.2 认证与 SDK 环境组合

- 强制终端认证开启时，`BrokerID`、`UserID`、`AppID`、`AuthCode` 必须正确；认证通过后才能登录。`UserProductInfo` 是否仍被使用，由目标期货公司要求决定。[O12]
- AppID/AuthCode 不是可随意跨环境复用的通用密码。可能绑定产品、账户、直连/中继类型和生产/评测环境。
- 生产与评测前置、动态库、采集库、`bIsProductionMode` 必须按期货公司提供的组合使用。旧版官方 FAQ 已明确评测和生产密钥不同；不能仅凭“版本号更高”混用。[F2]
- 断线重连需要重新认证、相应信息上报和登录；不能沿用旧进程内布尔值。[F2]
- 连续认证/登录失败要退避并告警。反复错误密码可能触发账户或 IP 封禁，自动重试会扩大故障。[P5]

### 3.3 行情登录成功不代表凭据正确

行情接口默认可用空结构体登录；CTP 6.6.2 起柜台可开启行情身份校验，开启后才要求正确的 BrokerID/UserID，并可能要求与交易登录及 IP 条件一致。因此 SimNow 上“错误密码也登录成功”不是生产漏洞，也不能证明生产行情不校验。[O13]

### 3.4 结算确认按交易日，不按进程

当前文档要求每日开始交易前确认上一交易日结算单，只需一次。成熟做法是：

1. 登录后查询 `ReqQrySettlementInfoConfirm`；
2. 当前交易日未确认时再调用 `ReqSettlementInfoConfirm`；
3. 确认失败不得进入 `Ready`；
4. 跨交易日仍在运行的进程必须重新检查，不能只在 `main()` 启动时做一次。[O9][G2]

其他人工终端可能已完成确认，所以“本进程没确认”不等于“柜台未确认”。

### 3.5 会话数和订单命名空间

- 同 UserID 的最大在线会话数由柜台配置，手机、人工客户端、旧进程、测试网关都可能占用。[F1]
- 一个账户可被多个终端同时使用。柜台查询可能返回非本进程报单，不能把所有委托都假设为本地策略创建。
- 每个会话独立维护 `FrontID + SessionID + OrderRef`。重连得到新会话后，旧三元组不能被改写成新会话继续使用。
- 跨会话撤单优先使用回报中的 `ExchangeID + OrderSysID`；当前文档也推荐 OrderSysID 方式。不要去掉或重排 OrderSysID 原有字符。[O7]

## 4. 请求标识、报单标识与持久化

### 4.1 三套标识不能混用

| 标识 | 用途 | 典型误区 |
|---|---|---|
| `nRequestID` | 关联一次主动请求和 `OnRsp*` 直接应答；聚合查询批次 | 拿它匹配 `OnRtnOrder` / `OnRtnTrade` |
| `FrontID + SessionID + OrderRef` | 标识本地会话内报单 | 多线程无序分配、跨会话复用、进程重启撞号 |
| `ExchangeID + OrderSysID` | 柜台/交易所侧报单定位，适合跨会话撤单和关联成交 | 转换为整数后丢前导字符，或未等回报就假设存在 |

业务系统还应有自己的 `client_order_id`，用于跨进程重启、跨会话和审计。它不能替代 CTP 字段，而是保存映射关系。

### 4.2 OrderRef 分配纪律

- 必须是数字字符，并在同一会话内严格递增；多生产者必须先串行化分配，再发送。[G2][O6]
- 推荐只有一个分配者，分配、写入本地日志和发送按统一顺序执行。
- 保存原始字符串和数值两种形态时，要明确前导零、最大长度和溢出规则；不要用浮点解析。
- 新会话可参考登录回报中的 MaxOrderRef 和当前柜台规则重新建立序列，但不能把旧会话的最大值无依据地套到新会话。
- `OrderActionRef` 同样需要单调管理；批量、报价、行权等扩展业务应按当前字段文档确认各自命名空间，不凭名称推断。

### 4.3 最小持久化模型

至少持久化以下事件，而不只是最终订单表：

```text
本地委托意图 -> 分配 OrderRef -> Req 返回值 -> 直接应答
-> 每次报单回报 -> 每笔成交回报 -> 撤单意图与结果 -> 对账修正
```

每条记录带环境、BrokerID、InvestorID、交易日、接收时间、原始关键标识和载荷版本。这样断线后才能区分“从未发送”“已发送无结果”“已明确拒绝”“已有成交”。

## 5. 报单与撤单：生产状态机

### 5.1 三类结果必须分开

| 结果 | 例子 | 是否可自动重发同业务意图 |
|---|---|---|
| 明确未发送 | 本地参数校验失败；可确认发送前已断线 | 修正后由业务规则决定 |
| 明确拒绝 | `OnRspOrderInsert`、相应 `OnErrRtn`、交易所拒单状态 | 不修正原因则重发只会再次拒绝 |
| 结果不确定 | 返回 0 后超时、断线、进程崩溃、应答丢失 | **不可直接重发；先查报单与成交** |

`Req*` 的非 0 返回值必须记录，但也不要把“返回 -1”在所有语言封装里一概等同于柜台绝无订单；若断线与发送存在竞态，仍应通过对账排除已到达的可能。[O6]

### 5.2 拒单和状态通知路径

完整消费以下路径：

- `OnRspOrderInsert`：直接错误应答，带 `nRequestID`；
- `OnErrRtnOrderInsert`：错误回报，按报单标识关联；
- `OnRtnOrder`：正常状态、CTP 状态变化和交易所拒单/被动撤单等；
- `OnRtnTrade`：实际成交事实。

撤单同理处理 `OnRspOrderAction`、`OnErrRtnOrderAction` 和 `OnRtnOrder`。解析时先判断 `RspInfo` 和空载荷，不能在有错误时直接解引用可能为空的数据结构。

### 5.3 不要假设一笔订单只有一条状态回报

CTP 可先推自身状态，再推交易所状态；同一状态可再次出现。官方回调规则还列出了立即成交、部分成交、FAK、重复撤单和不同交易所的特殊序列。[O8][G2]

实现要求：

- 报单更新是**状态归并**，不是每收到一条就增加一次成交量；
- 用 `VolumeTraded` 等字段做一致性检查，但资金、持仓和成交统计以独立成交回报去重后的结果为准；
- `AllTraded`、`Canceled`、`NoTradeNotQueueing`、`PartTradedNotQueueing` 都不能当作普通活跃挂单；
- `Canceled` 还要结合 `OrderSubmitStatus` 和 `StatusMsg` 区分正常撤销与拒单；
- 收到未知订单的成交时先挂起关联并触发对账，不能丢弃或崩溃；
- 终态与迟到成交的竞态要有对账修正，不允许累计成交量变小而无人告警。

### 5.4 报单字段和交易所差异

`ReqOrderInsert` 必填的不只是合约、方向、价格和数量，还包括 ExchangeID、开平、投机套保、价格条件、有效期、成交量条件、触发条件、强平原因等。所有请求结构体先零初始化，再显式填字段，避免未初始化垃圾值。[O6]

- 限价、市价、FAK、FOK、GFD、IOC 不是所有交易所、品种和时段都支持；以目标交易所和柜台当前规则为准。
- FAK 可以部分成交后撤销余量，不能把“有撤单状态”解释为整单无成交。
- `CombOffsetFlag`、`CombHedgeFlag` 是数组语义，单腿通常使用首元素，不能按普通单字符字段处理。
- 上期所和能源中心区分平今/平昨；其他交易所的普通平仓指令与 CTP 转换规则不同。CTP 接受转换不代表客户端可以忽略真实今昨仓和费用差异。[O6]
- 价格最小变动价位、单笔上下限、涨跌停、交易编码、权限和账户风控都应在报单前检查，但本地检查不能替代柜台结果。
- 郑商所价格截取等特殊行为只用于解释对应版本文档，不应推广到其他交易所。[O6]

### 5.5 撤单竞态

- 已撤、已全成或已在撤单途中，再次撤单可能被拒；重复拒绝不应触发无限撤单循环。
- 撤单请求到达前的最后成交仍然有效，所以“已发撤单”不等于剩余量安全。
- 某些版本/交易所对“未知单”撤单有限制，不能用一个固定顺序覆盖所有柜台。[O7]
- 断线恢复后先找到真实报单，再决定撤单；不要仅凭本地旧状态向新会话发旧 OrderRef。

### 5.6 对冲设置、SPD 与套保确认

- **对冲设置仅适用于大商所。** InstrumentID、UnderlyingInstrID、ProductID 的填法随期权/期货、客户/品种/合约粒度和对冲类型变化；撤销时按原报入维度填写，不能简化为只传一个合约代码。[ReqOffsetSetting](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQOFFSETSETTING.html)、[ReqCancelOffsetSetting](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQCANCELOFFSETSETTING.html)
- 对冲设置的 RequestID 只是回显字段。同一“投资者+对冲粒度+对冲类型”后台只保留一笔，需要区分请求时由调用方使用 RequestID；Session 不应把这个结构体内字段静默覆盖成外层 nRequestID。
- 合约级期权/期货对冲且 IsOffset=true 时，Volume 有明确范围，99999999 表示全部手数；其他粒度不能机械套用同一校验。绑定层保留业务字段，由目标业务层按当前规则验证。
- SPD/套保申请及撤销必须同时消费直接应答、错误回报和状态通知；`OnRsp*` 只说明直接应答到达，不能替代 `OnRtn*` 状态。撤销保留原 OrderRef/OrderSysID，并用当前 FrontID/SessionID 只在 OrderRef 定位路径生效；跨会话仍需 OrderSysID。
- 本项目的 SPD/套保申请与既有报单家族共享 Session OrderRef 序列，这是**本地防撞号设计**，不是从稀缺资料推断出的新柜台规则。结构体内 RequestID 保留调用方值。
- 分类合约查询只有 TradingType、ClassType 是文档确认的过滤条件；CombPromotionParam 的 ExchangeID/InstrumentID 在文档中也不是过滤字段。封装层原样传递，不擅自扩展成本地筛选或删除返回行。

## 6. 成交、订单去重与恢复竞态

### 6.1 推荐成交唯一键

在单账户系统可用交易所和 TradeID 组合；多环境、多账户系统建议使用：

```text
(environment, broker_id, investor_id, trading_day, exchange_id, trade_id)
```

具体字段空值和唯一性需按目标交易所验证。数据库建立唯一约束，应用收到重复记录时做幂等跳过，而不是只在内存 `HashSet` 去重。

报单回报不应使用同样的“每条只处理一次”思路，因为相同状态的多次通知可能携带不同补充信息。应对报单做版本化归并，对成交做唯一事实去重。

### 6.2 启动快照与实时流的重叠

QUICK 加查询恢复时，常见错误是“先查询，再开始处理回报”，中间产生空窗；或“查询和回报同时直接写”，导致重复。推荐：

1. 登录后保持私有流接收，但先缓冲或进入可幂等处理通道；
2. 查询当日报单、成交、持仓和资金，得到柜台快照；
3. 按订单键和成交键合并快照与缓冲增量；
4. 校验未知订单、未知成交和数量差异；
5. 完成后才进入 `Ready`。

RESTART/RESUME 也要做业务幂等，因为应用数据库可能只提交了一半，或流文件与数据库恢复点不同。

### 6.3 对账不是无限轮询代替事件

- 启动和恢复：完整对账；
- 盘中：低频或按异常触发对账，并遵守查询流控；
- 收盘：订单、成交、持仓、资金与本地账本核对；
- 历史跨日：CTP 当日查询不能替代企业自己的历史库和结算单归档。[G2]

## 7. 查询流控与多行聚合

### 7.1 流控不止“每秒一次”

旧客户端指南给出“每秒一次、在途一笔”的基础限制。穿透式版本后，每秒查询数可由前置配置，但 API 仍内置在途查询一笔；此外还有：

- 报单/撤单频率控制；
- FTD 总报文流控，超限可能延迟而不显式报错；
- 同 IP 的前置连接频率；
- 同 UserID 最大会话数；
- 交易所侧报单/撤单流控。[G1][F1]

因此不要把所有延迟都解释成网络，也不要通过盲目增加会话绕过限制。报撤单限额通常按投资者等更大范围统计，新增会话可能反而触发会话上限。

### 7.2 查询调度器

建议所有 `ReqQry*` 进入统一调度器：

- 单 API 实例只保留一个在途查询；
- 每秒速率可配置，默认保守，不用忙等和紧循环；
- 区分高优先级的恢复对账与低优先级周期刷新；
- 每次请求有总超时和取消原因；
- -2/-3 和异步 `OnRspError` 都进入调度结果；
- 查询可以重试，因为查询本身幂等，但重试也必须限速；
- 不在 SPI 回调里睡眠等待下一次查询。

### 7.3 聚合规则

Session 将每个查询响应行立即转发给调用方，不持有或发布整批结果，也不提供底座聚合器；以下聚合与快照规则全部由调用方实现。

- 以 `nRequestID + 响应类型` 定位批次，直到 `bIsLast`；
- 空结果、空载荷、被本地过滤的行仍要完成批次状态推进；
- Session 将 `OnRspError` 映射为携带 request_id 的 `QueryError`，调用方命中在途请求时立即失败出队；
- 断线时全部在途查询以连接中断结束；
- 每批持仓/账户结果使用新缓冲，不能把上一快照残留继续累加；
- 发布前检查错误、类型混杂、重复批次和必要字段，失败不能当成“空持仓”。

## 8. 行情数据陷阱

### 8.1 快照不是逐笔，也没有历史回补

CTP 普通期货行情是切片快照，不是完整逐笔委托/成交流。不要把固定的“500ms 两条”写成所有交易所、版本和环境的协议保证，也不要用快照反推出全部市场事件。

CTP 不提供历史行情，也未及时登录或断线造成的行情丢失不提供回补；有完整性要求时需其他历史数据源、多路采集或明确的数据缺口标记。[G2]

### 8.2 累计字段与无值字段

- `Volume`、`Turnover`、`OpenInterest` 是行情快照字段，其中成交量/成交额通常按交易日累计；增量要以上一有效快照计算，并处理交易日切换和异常倒退。
- double 极大值（常见为 `DBL_MAX`）表示无值，不是真实价格。涨跌停时某侧盘口无价可能同时出现极大值和量为 0。[O11]
- 结算价、收盘价在盘中可能无值；不同交易所推送时机和 UDP/TCP 字段支持不同，不用“非 0”判断有效性。[O11]
- 价格计算优先使用定点整数或十进制类型；浮点仅用于展示时也要避免误差进入 PriceTick 校验。

### 8.3 日期和时间戳

`TradingDay`、`ActionDay`、`UpdateTime`、`UpdateMillisec` 必须保留原值。夜盘属于后续交易日，但各交易所字段口径存在差异；大商所日期处理已有成熟框架 issue 讨论，不能用一个“全部取本地日期”或“全部取 ActionDay”的规则解决。[P2]

每条行情至少保存：

- 原始交易日、业务日期和交易所时间；
- 本地墙钟接收时间（带时区）；
- 本地单调时钟或序号，用于延迟和乱序分析；
- 来源网关和连接代次。

服务器应校时，但校时不能修正上游字段本身的语义。跨午夜、长休、盘前无时间戳快照都应纳入测试。

### 8.4 合约与订阅

- 每日获取并版本化合约表，使用 `VolumeMultiple`、`PriceTick`、上下限、限价单数量上下限、到期日和产品类型等真实字段。
- 合约、费率、交易权限可能变化，缓存必须带交易日和获取时间；夜盘和日盘前可按业务需要刷新。
- 行情重连后重新登录并重放去重后的订阅集合，同时处理 `OnRspSubMarketData` 错误。
- 在合约元数据尚未就绪时，可缓存或标记行情，不能因查不到乘数而崩溃；也不能悄悄用默认乘数。
- 标准 CTP 普通行情不等于 Level-2 或组播低延迟服务，相关能力需向期货公司单独确认。[G2]

## 9. 持仓、资金、费用与组合

### 9.1 持仓多行聚合

CTP 按合约、持仓方向、开仓日期汇总；上期所和能源中心区分今昨仓。一个合约同一方向可能有多行，直接覆盖会丢仓，无视批次重复累加会翻倍。[O10]

推荐先保存原始行，再按完整业务键聚合：

```text
账户 + 合约 + PosiDirection + PositionDate/今昨属性 + 必要的投资单元维度
```

- `YdPosition` 是开盘前初始昨仓，不是当前剩余昨仓；通用文档给出的当前昨仓为 `Position - TodayPosition`。[G2]
- SHFE/INE 的今昨分行与其他交易所有差异，成熟网关也专门处理，不能一套条件覆盖所有交易所。[P1][P3]
- 每次完整查询后替换快照；不要在上次发布结果上继续加。
- 总持仓不等于可平。未成交平仓单会冻结仓位，本地未确认意图也应纳入风险占用，但对账时不能与柜台冻结重复计算。
- 持仓明细中的平仓量、成本和组合持仓字段有专门语义，不从字段名猜算法；必要时以结算单验证。

### 9.2 资金与费用

- 使用柜台 `Available` 等字段做账户事实展示和风控输入，不用简化公式重算后覆盖柜台。
- 冻结保证金、冻结手续费、冻结资金、平仓/持仓盈亏、入金出金要分别记录，避免把 Balance、Available 和可提资金混为一谈。
- 投资者保证金率和手续费率可能包含期货公司加收、按品种或合约特殊设置，并可能动态调整；交易所公开费率不能替代投资者查询结果。
- 费率查询无结果不能解释为“免费”；可能是查询条件、权限或数据未就绪。
- 报单前本地估算是风险防线，最终以柜台实际冻结、成交费用和结算为准。
- 组合合约可能同时出现组合与单腿记录，保证金不能简单相加；组合优惠和持仓字段需按交易所及柜台规则单独验证。

### 9.3 费率与组合保证金查询的接口边界

- **合约保证金率/手续费率不是全市场一次导出接口。** `ReqQryInstrumentMarginRate` 的 InstrumentID 为空时返回持仓相关合约；查询保证金率还必须正确填写 HedgeFlag。`ReqQryInstrumentCommissionRate` 空合约同样只覆盖持仓相关合约。若柜台按品种配置手续费，响应 InstrumentID 可能是品种代码而非请求合约代码，客户端不能据此认定响应错位。[合约保证金率文档](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQQRYINSTRUMENTMARGINRATE.html)、[合约手续费率文档](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQQRYINSTRUMENTCOMMISSIONRATE.html)
- **交易所费率、投资者费率和合约元数据中的费率不是同一层事实。** 实际冻结/占用优先参考投资者合约保证金率；交易所保证金率和调整率用于解释或计算中间过程。不能因为几个字段名称相近就相互替代。[VeighNa 费率查询实践](https://www.vnpy.com/forum/topic/7684-ctpjie-kou-zhi-bao-zheng-jin-lu-shou-xu-fei-lu-cha-xun)
- **期权交易成本查询的结果是估计值。** InputPrice 参与权利金部分计算，资金查询中的期权保证金可能使用 max(昨结算、最新价) 等不同价格口径，两者存在差异时不能直接判为柜台错误。[期权交易成本文档](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQQRYOPTIONINSTRTRADECOST.html)
- **SPBM/SPMM/RCAMS/RULE 参数按“交易所参数”和“投资者参数”分层。** 例如 SPBMFutureParameter 不含 BrokerID/InvestorID，而 SPBMInvestorPortfDef、InvestorProdSPBMDetail 含账户身份；封装层只能覆盖结构中实际存在且属于会话身份的字段，不能给所有请求机械添加同一组参数。[SPBM 期货参数](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQQRYSPBMFUTUREPARAMETER.html)、[SPBM 投资者套餐](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQQRYSPBMINVESTORPORTFDEF.html)
- **多行不总是异常。** InvestorPortfSetting 的返回记录是交易编码级，中金所可能多条；InvestorInfoCommRec 对同一投资者和商品代码可分别返回期货与系列期权两条记录，IsOptSeries 用于区分。聚合时保留原始行，不按投资者+品种强行去重。[组合保证金开关](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQQRYINVESTORPORTFSETTING.html)、[申报费阶梯记录](https://ctp.madongdong.com/6.7.11_API/JYJK/CTHOSTFTDCTRADERAPI/REQQRYINVESTORINFOCOMMREC.html)
- 本批 Session 只负责身份一致性、请求发送和回调类型逐行保全，不在绑定层聚合视图或推导组合保证金、申报费。具体模型算法、参数有效期、批次完整性和交易所适用性由业务层按目标柜台验证。

## 10. 银期转账

1. 将 `OnRsp*ByFuture` 视为受理应答，将 `OnRtn*ByFuture`、错误回报和后续流水视为处理结果来源。
2. 为每次业务转账持久化唯一流水和状态；`future_serial` 等字段按目标柜台规则维护，不能因 SimNow 接受 0 就认定生产也接受重复值。
3. 超时、断线或进程崩溃后先查 `ReqQryTransferSerial` 和资金，不得直接再次转账。
4. 把冲正作为独立业务事件处理，原转账、冲正和最终资金应能串联审计。
5. 银行、期货公司的开放时段、金额/次数限制、资金密码和签约状态均可能不同；这些不是 CTP API 通用常量。[P5]
6. 生产自动转账应比报单有更严格的人工限额、双人复核或禁用策略，异常时优先停止新转账。

## 11. C++ / Rust / FFI 与部署陷阱

### 11.1 回调与线程

- SPI 回调只做必要校验、owned 化、时间戳、持久化投递或非阻塞入队；不要同步等待同一线程才能完成的应答。
- 不要在持锁状态下调用用户回调，而另一个线程需要同一把锁才能发送或释放。
- 即使旧指南曾描述部分 API 可多线程调用，当前个别接口文档仍有“不是线程安全”的说明。封装层采用单线程串行化 API 调用更容易证明正确，也能保证 OrderRef 分配顺序。[G2][O12]
- Rust panic、C++ 异常不得穿过 C ABI 回调边界；桥接层应捕获并上报，否则可能直接终止进程。
- 业务慢消费者不能反向阻塞 CTP 回调。行情可定义丢弃/合并策略，订单和成交则必须持久化、背压或停止策略，不能静默丢弃。

### 11.2 生命周期

- SPI 对象必须比 API 所有潜在回调活得更久；释放顺序可参照旧官方指南：先 `RegisterSpi(NULL)`，再 `Release()`，最后销毁 SPI，但封装层仍需按当前版本验证。[G2]
- 不在 SPI 回调中直接销毁正在回调的 API；把关闭命令交给控制线程。
- `Init` 是启动连接，`Join` 是等待接口线程结束，不能把 Join 当成普通“初始化完成”。
- 避免重复 `Init`、多个关闭路径并发和 Drop 后回调仍访问已释放 Rust 对象。
- 关闭时区分本地 Release、业务登出和进程退出；旧版本登出可能触发重连，不能把它当唯一关闭手段。

### 11.3 结构体、定长字符串和编码

- CTP POD 请求结构体先零初始化；复用回报结构体构造新请求时，清除所有服务端分配字段。
- 定长 `char[]` 不一定有额外 NUL 空间。绑定应按字段边界读取，不能盲目 `strlen` 或 `CStr` 越界。
- 中文合约名、StatusMsg、ErrorMsg 通常需要 GBK 解码；统一在桥接层转换并保留错误 ID。
- OrderSysID、OrderRef 等标识按字符串保存，不去空格、不转浮点；只有协议明确允许时才做数值递增运算。
- 输入超长、包含 NUL、非法 GBK 字符时要在本地报错，不能静默截断成另一个合约或账户。

### 11.4 SDK 与运行时一致性

每次构建和发布都绑定一组完整产物：

```text
头文件 + 静态/导入库 + 实际加载的 DLL/SO/DYLIB
+ 商密/非商密类型 + 生产/评测模式 + 架构 + 桥接层源码
```

- 启动记录 `GetApiVersion`、库文件哈希、实际搜索到的库路径、目标环境和构建版本。
- Windows 检查 DLL 搜索顺序、VC++ 运行库和位数；Linux 检查 `ldd`、rpath/`LD_LIBRARY_PATH`、glibc/libstdc++ 符号和文件句柄；macOS 检查 dylib install name、签名和架构。
- 4097 不是“版本错误”的专属码，但版本/密钥/前置不匹配确实可能表现为连接或解密失败，需要结合发生阶段排查。[F2]
- 不在交易时段直接覆盖生产动态库或切换 SDK；升级需经过目标期货公司测试环境、完整回归和可回滚发布。

## 12. 日志、监控与可诊断性

### 12.1 必须记录的字段

- 环境、BrokerID、脱敏 UserID/InvestorID、API 版本、前置标识、进程实例 ID；
- 连接代次、FrontID、SessionID、断开 reason、认证/登录/结算/对账状态；
- `nRequestID`、Req 返回值、ErrorID、解码后的 ErrorMsg、回调类型、bIsLast；
- client_order_id、OrderRef、OrderSysID、TradeID、原始状态与状态消息；
- 上游时间、本地接收时间、处理完成时间、队列深度和持久化结果。

密码、AuthCode、资金密码、完整银行账号、终端采集敏感信息不得明文写日志。排障需要原始报文时也要脱敏并控制保留期限。

### 12.2 生产告警

至少监控：

- 传输、认证、登录和 `Ready` 状态分离；
- 重连次数、连续失败、会话数超限和认证失败；
- 各交易所最后行情上游时间/接收时间，无行情与休市区分；
- 最后订单/成交回报时间，不等于用固定超时推断必有成交；
- 结果不确定订单数、未知成交数、对账差异、重复成交拦截数；
- 查询失败、超时、在途数量和调度延迟；
- 队列深度、丢弃、持久化延迟、磁盘和 flow 文件异常；
- 本地风险拒绝与柜台拒绝分别统计。

错误码用于检索，ErrorMsg 用于诊断；随包 `error.xml` 应与 SDK 一起版本化，不能只维护一张来源不明的网表。[L1]

## 13. 测试体系：把生产异常提前制造出来

### 13.1 本地自动化必测场景

| 类别 | 场景 | 通过标准 |
|---|---|---|
| 回报乱序 | 立即全成、先成交后本地订单可见、撤单与成交交叉、未知订单成交 | 不崩溃、不丢成交，最终可由对账收敛 |
| 重复 | RESTART 全量重放、同一 TradeID 重投、同状态订单重复 | 成交只记一次，订单不重复增加量 |
| 断线 | 认证中、登录中、查询中、报单后应答前、初始对账中 | 立即非 Ready，在途查询结束，报单进入不确定而非失败 |
| 流控 | -2、-3、异步 OnRspError、FTD 延迟模拟 | 查询有界重试；交易不盲目重发 |
| 聚合 | 空结果、空载荷、bIsLast 单行/多行、错误后无末行 | 不错误发布空快照，不永久挂起 |
| 持仓 | SHFE/INE 今昨分行、其他交易所混合仓、冻结、组合 | 总仓、今昨仓、可平与预期一致 |
| 日期 | 夜盘跨午夜、节假日、空 ActionDay、各交易所样本 | 原始字段保留，时间排序不跳日 |
| 重启 | 发送前崩溃、发送后崩溃、数据库已提交/未提交、流文件失效 | 恢复不重复下单、不重复记账，有差异告警 |
| 并发 | 多策略同时发单、关闭与回调并发、慢消费者 | 引用单调、无死锁、无 FFI 生命周期错误 |
| 编码 | 最大长度字符数组、GBK 中文、NUL、DBL_MAX | 不越界、不乱码、不把无值当价格 |

### 13.2 SimNow / 兼容环境测试

适合跑基本认证登录（若该环境要求）、订阅、合约查询、普通报撤单、FAK/FOK（若支持）、断线重连和长时间运行。记录环境、日期、前置、SDK 版本和实际结果。

不应把下列结论写成“CTP 一定如此”：

- 错误行情密码也能登录；
- 某接口填 0、空值或非法今昨标志总能通过；
- 某组前置全天在线；
- 模拟环境的撮合、费率、延迟、滑点与生产一致；
- 某种回调顺序在一次测试中未变，所以永远不会变。

### 13.3 期货公司仿真 / 穿透式评测

上线前至少确认：

- 目标生产 API 包、评测包和 `production_mode` 的准确组合；
- AppID/AuthCode 的账户与环境绑定、直连/中继模式、终端采集要求；
- 生产前置、备用前置、FENS、SSL/代理及网络白名单；
- 账户交易所/品种/期权权限、套保或投机属性、最大会话数；
- 查询、报撤单、连接和 FTD 流控的实际配置或保守预算；
- 支持的订单类型、今昨仓、组合、预埋单和银期业务；
- 结算确认、密码修改、首次登录、清流和日常维护时间；
- 期货公司技术支持升级路径和故障联系人。

### 13.4 生产验证边界

生产只做经过审批的小额、限量、可撤销验证，并先验证风险开关和人工接管。不要在生产随意拔网、杀进程、制造重复报单或重复转账来“测试恢复”；这些场景应在本地和仿真完成，生产故障演练须与期货公司约定窗口和方案。

## 14. 生产上线与值班手册

### 14.1 盘前检查

- [ ] 交易日历、合约到期、交易所公告和期货公司维护通知已检查。
- [ ] 配置指向预期环境；测试 AppID/AuthCode、前置和 flow 不会混入生产。
- [ ] 二进制、配置、SDK 和动态库哈希与已审批版本一致。
- [ ] 服务器时间、时区、磁盘、文件句柄、flow 目录和日志轮转正常。
- [ ] 旧进程、备用进程和人工终端不会重复执行同一策略；会话预算充足。
- [ ] 认证、登录、结算确认和初始对账完成，未确认订单/成交已处理。
- [ ] 柜台持仓、资金与本地账本一致；其他终端订单已识别。
- [ ] 单笔、单日、品种、账户级限额和总开关有效。
- [ ] 行情新鲜度、订单/成交持久化、告警和人工接管可用。

### 14.2 上线与回滚

- 新旧实例不要无协调地同时运行同一策略；即使 flow 分开，也可能重复报单和争抢会话。
- 回滚不仅是换二进制，还要确认数据库格式、订单映射、flow 序号和配置是否兼容。
- 升级 SDK 后必须重新做认证、报撤单、恢复和跨交易日测试，不能只验证编译通过。
- 保留已验证的旧制品，但不要自动回滚并立即重放所有未确认策略意图。

### 14.3 故障处置

**断线**：停止新策略意图 -> 保留在途证据 -> 等自动/受控重连 -> 重新认证登录 -> 对账 -> 人工或规则确认后恢复。不要频繁 Release/Init 形成连接风暴。

**订单结果不确定**：冻结该意图重试 -> 查当日报单与成交 -> 关联 OrderRef/OrderSysID/TradeID -> 修正本地状态 -> 再决定是否生成新的业务意图。

**持仓或资金不一致**：停止相关品种或全部新开仓 -> 获取新快照 -> 检查是否重复聚合、漏成交、其他终端交易 -> 以柜台事实修正并保留审计。

**持续拒单**：按 ErrorID、StatusMsg、合约、权限、资金、频率分类；停止同源自动重试，避免触发进一步风控。

**行情停止但连接正常**：核对交易时段、合约状态、订阅应答、上游时间和回调队列；不要仅因 TCP 未断就判断行情健康。

**转账结果不确定**：禁止重发 -> 查流水和资金 -> 联系期货公司/银行 -> 处理可能冲正并完整留痕。

## 15. 对 ctp-base 后续开发的直接建议

现有托管层已经具备一些正确基础：SPI 快速入队、actor 串行化、查询逐行公开、`OnRspError` 与断线原样转发、恢复事件和显式错误返回。批次聚合、超时与完整性由调用方负责。SimNow 相关实测继续保留在 [开发 FAQ](FAQ.md)，但不要替代以下生产能力。

### P0：真实交易前必须补齐或由使用方明确承担

1. **不确定订单状态**：发送后断线/超时不能简单报错即结束；保存发送意图和返回值，提供查询对账入口。
2. **持久化与幂等**：订单事件日志、成交唯一约束、进程重启恢复；内存事件通道不是账本。
3. **启动/恢复门槛**：`Recovered` 只能表示连接链恢复，不应被策略直接理解为对账完成；增加独立的同步完成状态。
4. **私有流策略**：明确当前模式、flow 目录隔离、RESTART 重放去重、RESUME 清流和 QUICK 补查方案。
5. **跨会话撤单**：完整保存并使用 OrderSysID，不能只保留当前 FrontID/SessionID。
6. **生产风险控制**：结果不确定禁止自动重发、重复信号去重、报撤单频率和账户级总开关。
7. **全路径错误消费**：直接应答、错误回报、OnRtnOrder 拒单和迟到成交统一归并，不能只映射“成功事件”。

### P1：上线质量

1. 集中查询调度、可配置速率、批次总超时和恢复查询优先级。
2. 合约/费率按交易日版本化；行情 DBL_MAX、空时间戳、累计量和跨交易所日期防御。
3. 持仓按原始行重建快照，专门覆盖 SHFE/INE 今昨仓和冻结量。
4. 连接代次与结构化审计日志；记录 API 版本、库哈希、FrontID/SessionID、RequestID 和三类订单标识。
5. 用 fake SPI 做重复、乱序、断线、崩溃恢复和跨日测试，而不只依赖在线 SimNow 测试。
6. 生产/评测配置和 SDK 组合做启动校验，防止测试凭据或动态库误入生产。

### P2：长期运维

1. 对账指标、未知订单/成交告警、行情新鲜度和持久化延迟监控。
2. 盘前、跨交易日、清流、SDK 升级和回滚手册。
3. 银期转账唯一流水、结果不确定处理和冲正对账。
4. 为不同期货公司保留经过验证的环境档案，但不把环境特有规则硬编码成全局协议常量。
